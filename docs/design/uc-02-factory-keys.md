# UC-2 – Evergreen Device IDs with Factory-Generated Keys

> Status: implemented in v0.1 (2026-10-23). Same flow as [UC-1](uc-01-evergreen.md); only the key
> generation differs.

## Difference to UC-1

| | UC-1 | UC-2 |
|---|---|---|
| Key pairs | generated by DTM (server-side) | generated by the factory; DTM only receives CSRs |
| Policy | `key_generation_option: server_side`, batch `input_type: csv` | `client_side`, batch `input_type: csr` |
| Single request | `server_side_key_gen: true` | `csr: <PEM>` + `subject.common_name` |
| Batch upload | ZIP with a CSV + `encryption_certificate` | ZIP with one `<CN>.csr` per device, no encryption certificate |
| Batch result | CMS envelope (`.p7m`), decrypted with the one-time key | plain ZIP (`Item-N-<file>.pem` + `full_results.txt`) – certificates only |
| Extra metric | – | key generation time on the factory side |

The demonstrator plays the factory: it generates the key pairs and CSRs locally (ECDSA P-256 or
RSA 2048, matching the issuing CA), uploads only the CSRs and discards the private keys right away.
They are never written to disk, sent to DTM or shown in the UI. The CSRs are offered as
`csrs.zip` (API runs: to replay the call; web UI runs: to upload in the portal).

## Verified live (2026-10-23)

- Policy with `client_side` key generation: created and deleted via `api-ui` like in UC-1.
- Single request with CSR: response has `pem`, `chain`, `serial_number` – no `private_key`.
- CSR batch (`input_format=csr`, ZIP of `.csr` files): job status starts as `pending` or
  `in_progress` (both seen live), then `completed`; 3 certificates in 1.2 s; 5 RSA certificates in 1.96 s.
- Result is a plain ZIP (`PK…`), no CMS envelope.
