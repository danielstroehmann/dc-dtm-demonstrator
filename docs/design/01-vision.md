# Vision – DTM Demonstrator

> Status: draft for discussion, as of 2026-10-23. Design phase – nothing is implemented yet.
> Basis: [../research/dtm-api-overview.md](../research/dtm-api-overview.md).

## 1. Goal

The demonstrator shows **typical DTM use cases end to end and reproducibly** – from the
configuration in Device Trust Manager to a device that holds and uses a certificate.
Instead of real hardware there are **simulated devices, each in its own Docker container**.

Example: "Evergreen certificate in manufacturing" once as a **batch with pre-generated
keys** and once via **EST** – the same business use case, two manufacturing variants side
by side.

## 2. Flow from the operator's perspective

1. **Pick a use case** (catalog with short description).
2. **Set parameters** – per use case, e.g. number of devices, key algorithm (RSA/ECC/PQC),
   certificate validity, authentication method.
3. **Configure DTM** – the demonstrator creates the required objects via API (certificate
   policy, authentication policy, device group …) and shows every step.
4. **Start devices** – one container per device; the devices run through the use case.
5. **Observe** – devices report their state to the host, the demonstrator shows it live.
6. **Clean up** – created DTM objects and containers are removed with one click.

## 3. High-level architecture (proposal)

```
┌──────────────── Host (Docker, behind reverse proxy + SSO) ───────────────────┐
│                                                                              │
│  Demonstrator                                                                │
│  ├─ Web UI  (use-case catalog, parameters, live view)                        │
│  ├─ Orchestrator                                                             │
│  │    ├─ DTM client        ──── REST (API key/mTLS) ───► DigiCert ONE / DTM  │
│  │    ├─ Container control ──► Docker API (via restricted proxy)             │
│  │    └─ Event collector   ◄──── status events from devices                  │
│  └─ ./data  (runs, created IDs, key material per run if needed)              │
│                                                                              │
│  Device 1 … Device N   (one container per device, shared device image)      │
└──────────────────────────────────────────────────────────────────────────────┘
```

**Use cases as data, not as code branches:** each use case is described declaratively –
parameters, DTM setup steps, device behavior, cleanup steps and the explanatory texts for
the presentation. New use cases come from a new definition, not from reworking the
orchestrator. DTM **blueprints are not used** (decided 2026-10-23, see `CLAUDE.md`).

## 5. Key question: what may a device do?

The requirement reads: *"The devices can do nothing except pass information to the host."*
That allows two readings, leading to very different demos:

- **A – devices are passive:** the host does everything on their behalf, including EST
  enrollment and key generation. Containers only hold state and report it.
  → Simple. For EST, however, this is wrong on the merits: the core of EST is that the
  device generates its own key and talks to DTM itself.
- **B – devices speak the device protocol, nothing else:** each container runs exactly the
  device-side part of the use case (generate key, EST/SCEP/ACME against DTM, TrustEdge if
  needed). Beyond that it has no logic, no UI and no inbound port, and it reports its state
  to the host.
  → Realistic, and the batch vs. EST difference becomes visible: with batch the device gets
  key and certificate "injected at the factory", with EST it fetches them itself.

**Decided (2026-10-23): B.** Devices are **low-resource "minions"**: no business function
(no simulated smart TV or similar), only the certificate management of the respective use
case plus the status report to the host. In batch use cases the device is automatically
passive, because the factory (= the host) does the work.

### Consequences for the device image

- **Minimal base image** (e.g. Alpine) with existing standard tools instead of custom code:
  `openssl` for keys and CSRs, `curl` for EST (EST is HTTPS plus PKCS#7/Base64, `curl` is
  enough), established clients for SCEP and ACME. Which clients exactly is still open.
- **Hard resource limits** per container (memory, CPU). Rough expectation: single to low
  double-digit MB per device. That makes a few hundred devices on a single host conceivable; this
  must be measured.
- **Lifetime follows the use case:** for one-time issuance the device reports the result and
  exits or idles. For renewal it sleeps until the next due date; an idle container costs
  practically nothing.
- **TrustEdge is the exception:** the agent is much heavier. Use cases with TrustEdge
  (e.g. no. 8) get their own image variant so the standard image stays small.

## 6. Further design decisions (proposals)

| Topic | Proposal | Rationale |
|---|---|---|
| Report channel device → host | Structured JSON lines on **stdout**, orchestrator reads them via the Docker API | Device needs no network access to the host and no extra channel; logs exist anyway |
| Live view in the browser | Server-Sent Events | One-way is enough, lightweight (Lighthouse 100) |
| Container control | Docker socket only via a **socket proxy** with an allowlist (create/start/stop/remove/logs) | Full socket access = root on the host |
| Device network | Own Docker network, outbound to DTM only, separate from the app network | Devices must reach neither the SSO nor other apps |
| Tagging | Every DTM object and every container carries a **run ID** (name/label) | Reliable cleanup, multiple runs distinguishable |
| Transparency | Every API call is shown in the UI (method, path, truncated body, no secrets) | For customer demos "this is what the call looks like" is often the key point |
| Key material (batch) | Only per run under `./data/runs/<id>`, deleted on cleanup | Demo keys, but handled cleanly anyway |
| Device image | One slim standard image (openssl, curl, SCEP/ACME clients), behavior via env; TrustEdge separate | One build, fast start of many containers, low resource usage |

### Account scoping (decided 2026-10-23, global)

The API key can access several DTM accounts. Every DTM call is explicitly scoped to the one
configured `account_id`; reads, writes and cleanup never touch other accounts. The UI always
shows which account is active.

### Naming convention (decided 2026-10-23, format still a proposal)

Everything created for a demo – DTM objects, certificate subjects, containers, networks,
files – is named `<prefix>-<run-id>-<use-case-specific-rest>`:

| Part | Proposal | Purpose |
|---|---|---|
| Prefix | fixed: `robot` (decided) | Recognize anything created by the automation |
| Run ID | freely chosen per demo, e.g. `acme`; default if left empty: 6 random characters `[a-z0-9]` (decided 2026-10-24 – DTM keeps names of deleted policies reserved, so IDs must not repeat) | Identify the demo run; target of the one-click cleanup |
| Rest | per use case, e.g. `est-devgroup`, `batch-dev-0042` | Readable in the DTM console during the demo |

Example: `robot-acme-est-dev-0007`. Characters limited to `[a-z0-9-]` – the spec
restricts at least one `name` field to `^[a-zA-Z0-9\s\-_]+$`; max. length to verify (one
field is limited to 255). Additionally, Docker labels carry prefix and run ID.
Cleanup finds its targets via this name pattern, and as a safety net matches against the
IDs recorded per run in `./data/runs/<run-id>`.
Proposed run-ID rules: `[a-z0-9]` only (no hyphen), max. ~16 chars, must be unique among
existing runs – otherwise `robot-acme-` would also match a run named `acme-2` during cleanup.

## 7. Open questions

1. ~~Reading A or B~~ → B, devices as low-resource minions (section 5).
2. **"Evergreen"** – does this mean a long-lived birth certificate from manufacturing
   (IDevID-like) that is never renewed? Or a certificate that keeps renewing itself
   automatically? This decides whether use case 4 belongs here or is a topic of its own.
3. **Batch with pre-generated keys:** the batch API supports both server-side key generation
   and factory-generated CSRs (CSV with `csr` column). Offer both as variants; DTM side still
   to be verified against the demo environment.
4. **Audience and mode:** does the use case run in one go, or step by step with "Next"
   (presentation mode)? For live demos I recommend step mode.
5. **Scale:** how many devices at most? With slim minions a few hundred containers are
   conceivable (to be measured). Device registration includes a license check – the tenant's
   license quota may be the real limit.
6. ~~DTM tenant~~ → **dedicated division for the demonstrator** (decided 2026-10-23).
   Open: certificate policies cannot be deleted via API – does `DELETE /division/{id}` remove them?
7. ~~Cleanup~~ → **fully cleanable with one click after every demo** (decided 2026-10-23).
   **Requirement:** everything a demo signs, issues or configures is rolled back; the account
   is left as it was before the demo. Open: some things cannot be undone via API –
   certificate policies (no delete endpoint), issued certificates (revocable, but remain as
   revoked records), audit log entries. Acceptable residue still to be defined (see 7a).
   7a. Definition of "restored" (accepted 2026-10-23): no *active* object remains (deleted
   where possible, otherwise revoked/disabled); history (audit log, revoked records) remains
   by design.
   7b. **Two cleanup modes** (decided 2026-10-23):
   - *Full* – restore the account as described above.
   - *Devices only* – delete devices and revoke their certificates (frees licenses), but keep
     the DTM configuration (division, policies, device groups) so it can serve as a
     reference configuration, e.g. for a customer.
   A run cleaned with *devices only* stays listed and can be fully cleaned later. Local key
   material and containers are removed in both modes. Open: do passcodes / auth certificates
   count as configuration (kept) or as credentials (removed)?
8. **Access:** only the author behind SSO, or do colleagues operate the demonstrator too?
9. ~~Language~~ → repo, docs and solution **fully English** (decided 2026-10-23, see `CLAUDE.md`).
